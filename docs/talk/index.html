Standing on Giants

Building a userspace TCP stack — and why the layers still matter

~60 minutes · TAP → ARP → IP → TCP → HTTP → (optional) TLS

Open with the brand. This is a teaching stack over Linux TAP, not a product pitch.

The networking stack lives in the kernel

Use the HTTP standard library, as a client or a server, in Go, Ruby or Node, and you hand the hard part to the operating system.

  • Your code builds a request. The kernel puts it on the wire: Ethernet, IP, TCP, the retransmits.
  • A userland process only reaches that stack through system calls: socket connect read write
  • Those calls are the whole API. The bytes on the wire are on the other side of them.

This talk is that other side.

The audience already uses net/http, Net::HTTP, or Node’s http module. Name the feeling: you wrote ten lines and a server appeared. Those lines never saw a packet. The kernel did. We are about to do the kernel’s job, badly and on purpose, so the syscalls stop being a wall.

It is all one string of bits

From the CPU, through the operating system, down into the networking stack. The same stuff, the whole way.

  • Ones and zeros, arranged so they mean something. A port. A promise to resend. A line of HTTP.
  • Look at the endless stream through a window of fixed length. Computation is that window stepping from one arrangement to the next.
  • The path of those arrangements is the work. One trajectory is a hard problem. Another is just hello world, drawn on a screen.

I think of that as a fundamental theorem of computation.

Slow down. This is your name for the idea, not a citation. The infinite tape and a fixed window are the same string, seen two ways. Hello world and a hard problem are both trajectories through its arrangements. CPU, scheduler, NIC, TCP: each one only moves that window. Land on the theorem line, then go to what they’ll leave with.

Background

Standing on giants

Nothing here was invented alone.

Great systems are built by many people

Every layer we lean on is the sum of decades of shared work.

  • Standards (RFCs) agreed between rival vendors, often after failures
  • One web request passes through a NIC, a kernel, a TLS library, curl and a CDN
  • Our few thousand lines stand on millions of hours

That isn’t a caveat. It’s the point.

Good protocols leave room for what comes next

They didn’t predict the future. They drew clean boundaries that later ideas could plug into.

Design choiceWhat it made possible
IP only promises best-effort deliveryReliability could be added on top (TCP)
TCP offers a plain stream of bytesNew apps never needed changes to IP
Every header has a “what’s inside” fieldEach layer can carry many kinds of next layer
TLS sits above TCPEncryption is optional

AWS replaced TCP underneath: SRD

Apps still open TCP sockets. Underneath, AWS can carry the traffic with its own protocol.

  • SRD (Scalable Reliable Datagram) runs on AWS’s Nitro network card
  • Sprays one flow across many network paths
  • Resends lost packets within microseconds, in hardware
  • Delivers everything, but out of order; the layer above puts it back in order

TCP isn’t mandatory everywhere. Neither is TLS.

Sources: AWS "A Cloud-Optimized Transport Protocol for Elastic and Scalable HPC" (IEEE Micro 2020); EFA and ENA Express docs. EFA exposes SRD for HPC/ML. ENA Express carries ordinary TCP/UDP flows between instances over SRD.

Where SRD sits under your TCP connection

your app     ── TCP socket          (API unchanged)
                     │
Nitro card   ── SRD                 multipath · fast retransmit
                     │              reliable, out-of-order
fabric       ── many paths at once
                     │
peer Nitro   ── reorder → hand TCP bytes up

With ENA Express, ordinary TCP traffic between instances rides on SRD without the app noticing. Because the layers are separate, AWS could replace the middle and leave both ends alone.

HTTPS is HTTP plus one optional layer

HTTP  ─┬─ straight on TCP     (-app http)
       └─ inside TLS on TCP   (-app https or -app https-diy)
                 ↑
         the same TCP code underneath

We added HTTPS late in the project, and nothing below TCP had to change.

The pattern

The onion interface

Every layer has the same shape, even without a shared Go interface type.

What “onion interface” means

Each layer is a header plus a payload.
In code it’s a struct with Parse (bytes → struct) and Marshal (struct → bytes).
It supports only a few operations.
Its payload is the next layer’s whole message.

Layers nest inside each other. A type field in each header says which layer comes next.

Each layer is an RFC. Its payload is the next one.

LayerDocumentWhat the payload can be
EthernetRFC 894IPv4, or ARP (RFC 826). The type field decides.
IPv4RFC 791TCP, or ICMP (RFC 792). The protocol field decides.
TCPRFC 9293A byte stream: HTTP (RFC 9112), TLS (RFC 5246), or a protocol nobody has written yet.
TLS 1.2RFC 5246HTTP again, now encrypted. Or something else that fits in a record.
HTTP/1.1RFC 9112A message. The body can carry yet another protocol.

A new layer is an agreement about how to read someone else’s payload. The layers outside do not change.

Reveal one row at a time: each payload is the whole message of the next RFC. Ethernet the frame is IEEE; RFC 894 is the rule that puts an IP packet inside it. The type field is the joint. TCP’s current text is RFC 9293, which obsoletes 793. HTTP semantics live in RFC 9110; 9112 is the wire format. The last row is the point: you can keep going. GRE, VXLAN, QUIC and SRD are all someone deciding what a payload means.

An Ethernet frame, as a Go struct

internal/eth/ethernet.go

// One Ethernet frame: a 14-byte header, then the payload
type Frame struct {
    Dst     net.HardwareAddr // who it's for (6-byte MAC address)
    Src     net.HardwareAddr // who sent it
    Type    uint16           // what's inside: 0x0806 ARP, 0x0800 IPv4
    Payload []byte           // ← the next layer's whole message
}

// bytes off the wire → struct
func Parse(b []byte) (Frame, error) { /* … */ }

// struct → bytes ready to send
func (f Frame) Marshal() []byte     { /* … */ }

Addresses, a type field saying what’s inside, and the payload. Every layer follows this pattern.

Parsing means reading bytes at fixed offsets

internal/eth/ethernet.go

func Parse(b []byte) (Frame, error) {
    // anything shorter than the 14-byte header can't be a frame
    if len(b) < HeaderLen {
        return Frame{}, fmt.Errorf("ethernet: frame too short")
    }
    // every field sits at a fixed position, so just copy it out
    return Frame{
        Dst:     append(net.HardwareAddr(nil), b[0:6]...),  // bytes 0–5
        Src:     append(net.HardwareAddr(nil), b[6:12]...), // bytes 6–11
        Type:    binary.BigEndian.Uint16(b[12:14]),         // bytes 12–13
        Payload: append([]byte(nil), b[14:]...),            // the rest
    }, nil
}

Choosing the next layer by its type field

internal/stack/stack.go

// the Ethernet payload is an IPv4 packet: parse its header
pkt, err := ip4.Parse(f.Payload)
// …

// IPv4's "protocol" field says what its payload is
switch pkt.Proto {
case ip4.ProtoICMP: // 1 = ICMP, e.g. ping
    return s.handleICMP(f.Src, pkt)
case ip4.ProtoTCP: // 6 = TCP: peel one more layer, hand it to TCP
    seg, err := tcp.Parse(pkt.Payload)
    // …
    return s.tcp.Handle(f.Src, pkt.Src, seg)
}

Each protocol only parses its own header. The stack package reads the type field and hands the payload to the right parser.

An ARP packet, as a Go struct

internal/arp/arp.go

// "Who has this IP?" (request) or "I do, here's my MAC" (reply)
type Packet struct {
    Op  uint16           // 1 = request, 2 = reply
    SHA net.HardwareAddr // sender MAC
    SPA net.IP           // sender IP
    THA net.HardwareAddr // target MAC (blank in a request)
    TPA net.IP           // target IP: the one being asked about
}

func Parse(b []byte) (Packet, error) { /* … */ } // bytes → struct
func (p Packet) Marshal() []byte     { /* … */ } // struct → bytes

ARP asks “who has this IP address?”, and the owner replies with its MAC address.

Answering “who has 10.0.0.2?”

internal/stack/stack.go · handleARP

p, err := arp.Parse(f.Payload)
// ignore replies, and questions about someone else's IP
if p.Op != arp.OpRequest || !p.TPA.Equal(s.cfg.IP) {
    return nil
}
// build the answer: "10.0.0.2 is at <our MAC>"
reply := arp.ReplyFor(p, s.cfg.MAC, s.cfg.IP)
// wrap it in Ethernet, addressed straight back to whoever asked
out := eth.Frame{
    Dst: p.SHA, Src: s.cfg.MAC, Type: eth.TypeARP,
    Payload: reply.Marshal(),
}
return s.writeFrame(out)

How an app plugs into our TCP

internal/tcp/app.go

// what our TCP calls when a connection has news
// (ConnKey = their IP, their port, our port)
type App interface {
    // bytes arrived: return bytes to send back, and whether to close
    OnData(key ConnKey, data []byte) (reply []byte, closeAfter bool)
    // the connection has ended
    OnClose(key ConnKey)
}

// the simplest app: send back whatever arrives, stay open
func (EchoApp) OnData(_ ConnKey, data []byte) ([]byte, bool) {
    return append([]byte(nil), data...), false
}

The app gets bytes, returns bytes, and says whether to close. Echo is the smallest one; next we put a protocol on top.

Adding HTTPS without changing the layers below

// runs once for each new TCP connection on port 443
func (s *DIYServer) serve(raw *tcp.StreamConn) {
    // wrap the plain TCP stream in our TLS
    tlsConn := mintls.Server(raw, s.cfg)
    // agree on keys first; give up if the handshake fails
    if err := tlsConn.Handshake(s.cfg); err != nil {
        return
    }
    // Read decrypts, then the same HTTP code as plain HTTP runs
    n, _ := tlsConn.Read(buf)
    reply, closeAfter := s.http.OnData(key, buf[:n])
    // Write encrypts the reply before handing it to TCP
    tlsConn.Write(reply)
}

TLS sits between TCP and HTTP. Neither of them had to change.

Deep dive

Peeling TLS

Another onion, with cryptography inside.

mintls: our own TLS 1.2 server, one cipher suite (ECDHE_ECDSA_WITH_AES_128_GCM_SHA256). We wrote the protocol; Go's crypto/* provides the primitives.

TLS has layers of its own

┌──────────┬─────────────┬────────────┬──────────────────────┐
│ type (1) │ version (2) │ length (2) │ payload              │
└──────────┴─────────────┴────────────┴──────────────────────┘
  type: 20 ChangeCipherSpec  21 Alert  22 Handshake  23 AppData

internal/mintls/record.go

// every TLS record starts with a 5-byte header
hdr := make([]byte, 5)
io.ReadFull(r, hdr)                      // block until all 5 arrive
typ  = hdr[0]                            // which kind of TLS message
vers = binary.BigEndian.Uint16(hdr[1:3]) // 0x0303 means TLS 1.2
n   := binary.BigEndian.Uint16(hdr[3:5]) // how long the payload is

// then read exactly that many bytes
payload = make([]byte, n)
io.ReadFull(r, payload)                  // ← the next layer's message

The TLS 1.2 handshake: agreeing on keys

sequenceDiagram participant C as Client participant S as Server C->>S: ClientHello · random, cipher suites S->>C: ServerHello · random, chosen suite S->>C: Certificate · X.509, P-256 public key S->>C: ServerKeyExchange · ECDHE key, signed S->>C: ServerHelloDone C->>S: ClientKeyExchange · ECDHE public key C->>S: ChangeCipherSpec + Finished · encrypted S->>C: ChangeCipherSpec + Finished · encrypted Note over C,S: HTTP inside AES-GCM records

That’s two round trips before the first byte of HTTP. TLS 1.3 cuts it to one.

The four jobs cryptography does in TLS

JobQuestionIn mintls
Key agreementHow do we share a secret over a wire anyone can read?ECDHE on P-256
AuthenticationAm I talking to the right server?ECDSA signature + X.509 cert
Key derivationHow do we turn one secret into many keys?TLS 1.2 PRF (HMAC-SHA256)
Record protectionCan anyone read or tamper with the bytes?AES-128-GCM (AEAD)

Each row is a field of study. We only glue them together.

Both sides compute a secret without sending it

internal/mintls/conn.go · Handshake

// a fresh key pair, used for this connection only
ecdhe, _ := ecdh.P256().GenerateKey(rand.Reader)
// send our public half, signed with the certificate's key so the
// client knows it's really us (ch = the parsed ClientHello)
ske, _ := marshalServerKeyExchange(ch.random, serverRandom,
    ecdhe.PublicKey().Bytes(), cert.PrivateKey)
// the client sends its public half back; combining it with our
// private half gives a secret only the two of us can compute
clientPub, _ := ecdh.P256().NewPublicKey(clientPubBytes)
preMaster, _ := ecdhe.ECDH(clientPub)
// mix in both randoms to get the 48-byte master secret
master := masterSecret(preMaster, ch.random, serverRandom)

The key pair is thrown away after each connection, so stealing the certificate key later can’t decrypt recorded traffic. This is called forward secrecy.

Turning one secret into four keys

internal/mintls/prf.go

// prf12 = TLS 1.2's pseudo-random function: HMAC-SHA256 in a loop,
// stretching (secret, label, seed) into as many bytes as we ask for
// step 1: shared secret → 48-byte master secret
func masterSecret(preMaster, clientRandom, serverRandom []byte) []byte {
    seed := append(clientRandom, serverRandom...)
    return prf12(preMaster, "master secret", seed, 48)
}
// step 2: master secret → 40 bytes, cut into four pieces
func keyBlock(master, clientRandom, serverRandom []byte) (...) {
    seed := append(serverRandom, clientRandom...)
    block := prf12(master, "key expansion", seed, 40)
    return block[0:16], block[16:32], // AES key: client→server, server→client
        block[32:36], block[36:40]    // IV prefix: same two directions
}

The Finished message is derived the same way from a hash of the whole handshake, so any tampering is caught.

Encrypting a record with AES-GCM

internal/mintls/record.go · seal (paraphrased)

// ("||" means "followed by")
// the nonce must never repeat under one key; seq counts records 0, 1, 2…
nonce := fixedIV(4) || seq(8)
// extra data the tag protects, even though it stays readable
aad := seq(8) || type(1) || version(2) || length(2)
// encrypt, and append a 16-byte tag covering ciphertext and aad
ciphertext := h.aead.Seal(nil, nonce, plaintext, aad)
h.seq++
// what actually goes into the record
record payload = explicitNonce(8) || ciphertext || tag(16)

The header isn’t encrypted, but it is checked. Reordering, replaying or changing a single bit makes decryption fail.

What we wrote vs what we borrowed

We wrote

  • Record framing and demux
  • Handshake state machine
  • Handshake hash and Finished checks
  • Key derivation (the PRF)

We used from Go (crypto/*)

  • AES and GCM
  • ECDH, ECDSA on P-256
  • SHA-256, HMAC
  • X.509 certificates

Build the protocol to learn it. Never write your own cipher code.

What mintls leaves out, and what TLS 1.3 changed

mintls doesn’t do

  • Any cipher suite but one
  • Resumption, client certificates, renegotiation
  • Proper error alerts
  • Protection against timing attacks

TLS 1.3 changed

  • One round trip instead of two
  • The certificate is encrypted too
  • New key derivation (HKDF), AEAD ciphers only
  • Forward secrecy is always on

Rabbit holes elliptic-curve math · AEAD design · PKI, cert chains, Certificate Transparency · side channels · post-quantum key exchange (hybrid ML-KEM)
